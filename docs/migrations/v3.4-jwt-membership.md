# Migration: v3.4.0 — JWT Authentication & Membership

This guide describes breaking changes introduced in v3.4.0. Apply it when upgrading from v3.3.x or earlier.

## 1. Session-based login replaced by JWT

The previous session/cookie logic has been replaced by JWT (JSON Web Token).

- After successfully logging in, clients must transmit the returned JWT in subsequent requests (e.g. in the `Authorization` header) instead of relying on a server-side session.
- Check your front-end and integration logic and adjust all auth flows (login, logout, token refresh, storage).

**Required environment variables** (set in `.env` or your deployment environment):

- `JWT_SECRET`
- `JWT_REFRESH_SECRET`
- `JWT_ALGORITHM`
- `JWT_EXPIRES_IN`
- `JWT_REFRESH_EXPIRES_IN`
- `JWT_ISSUER`
- `JWT_AUDIENCE`

See [Authentication](../api/authentication.md) for endpoint details.

## 2. Membership entity for user–tenant relationships

User lists previously stored directly on `Tenant` have been migrated to a new **Membership** entity.

The migration script `migrations/scripts/03-09-2025-migrate-users-to-memberships.js`:

- Creates a `Membership` document for each entry in `tenant.users` with: `tenantId`, `userId`, `roles`, `status = 'active'`, `source = 'invite'`.
- Creates or updates a membership with `owner = true` for all former `tenant.ownerUserIds`.
- Removes the fields `users` and `ownerUserIds` from all `Tenant` documents.

**Consequences:**

- Code that accessed `tenant.users` or `tenant.ownerUserIds` must use the `Membership` collection (queries on `tenantId` + `userId`, filters on `roles` or `owner`).
- Features affecting a user's roles or tenant affiliation should be mapped exclusively via `Membership`.

See the [Membership entity](../entities.md#membership) for the current schema.
