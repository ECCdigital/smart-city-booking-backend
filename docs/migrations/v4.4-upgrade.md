# Upgrade notes: v4.4

What an operator needs to know when upgrading an installation to v4.4.

## Favorites

New in v4.4
([ECCdigital/tickets#225](https://github.com/ECCdigital/tickets/issues/225)):
a signed-in user marks bookables and events as favorites and reads them in
the storefront's favorites list.

- `FAVORITES_MAX_PER_USER` is optional and defaults to 200: how many offers
  one user may mark across all tenants.
- No migration. The application creates the index of the collection
  `favorites` itself.
- Storefront 1.3.0 needs backend 4.4.0. Against backend 4.3.0 the heart
  reports „nicht verfügbar“ when a user marks an offer.
- Offers in the state `unlisted` (`isPublic` false) are reached in the
  storefront by the direct link to their checkout alone,
  `/checkout/<id>?tenantId=<tenant>`, no longer by their detail page.

## Salto KS open for setup

With Admin UI 4.4.0, Salto KS is open
([ECCdigital/tickets#571](https://github.com/ECCdigital/tickets/issues/571)):
admins of the tenant set it up themselves. The setup guide is the panel for
Salto KS in the Admin UI („Zutritt & Schließsysteme“, tab
„Schließsysteme“), with the prerequisites of the System-User before the
credentials; there is no other guide. Point admins and ECC operations there.

## Salto KS activations belong to their identity

Change of the IQ activations
([ECCdigital/tickets#573](https://github.com/ECCdigital/tickets/issues/573)).
An activation of a Salto IQ counts only for the site, the System-User and the
environment it was made under. After a change of one of them it rests, and it
counts again once the tenant is switched back; Salto hands out the first
secret of an IQ only once per System-User, so a lost activation could not be
made again. Rotating the client ID, the client secret or the password keeps
the activations, and so does naming the same site another way (UUID,
`site_uid` or `customer_reference`).

The migration `15-10-2026-stamp-iq-activation-identity` stamps the stored
activations with the identity their tenant names today, so the activated IQs
stay activated after the upgrade. It writes only entries without the stamp
and can run again.

### During the upgrade

- The migration needs Salto KS wherever a tenant with activated IQs names its
  site by `site_uid` or `customer_reference` instead of its UUID: it resolves
  the site through the list of sites at Salto. A site named by its UUID needs
  no call.
- When Salto KS cannot be reached, the migration stops before it writes
  anything, naming the tenant and the site, and the instance stays out of
  traffic (`/healthz/ready` answers `migrations: "failed"`). Start the
  upgrade again once Salto KS is reachable.

## Salto doors offer only „Per App“

Change of the access points
([ECCdigital/tickets#499](https://github.com/ECCdigital/tickets/issues/499)).
A Salto KS door offers the mode `remote` alone, at every lock type, keypad
locks included. The platform no longer creates a guest with a PIN in Salto KS
for a booking: that path never worked, since every Salto PIN hangs on a user
and the platform creates none.

There is no migration. An access point still stored with `authorization` or
`both` is skipped by the provisioning as not supported, and saving it again
with one of those modes is refused as `unsupported_mode`. Open Salto grants
are no longer taken back by the platform: the provider offers no revoke any
more, and the grant cleanup is gone (see
[Grant cleanup removed](#grant-cleanup-removed)).

### Before the deploy

Check every installation with `mongosh` against its database. Salto access
points with a mode other than `remote`:

```js
db.accesspoints.find({
  provider: "salto-ks",
  mode: { $in: ["authorization", "both"] },
});
```

Open Salto grants of bookings:

```js
db.bookings.find({
  accessInfo: {
    $elemMatch: { provider: "salto-ks", grant: { $ne: null }, revokedAt: null },
  },
});
```

Both have to come back empty. Otherwise:

- set each such access point to `remote`;
- clean up each open grant by hand in Salto KS, since the platform no longer
  takes it back.

## Grant cleanup removed

Change of the operation
([ECCdigital/tickets#580](https://github.com/ECCdigital/tickets/issues/580)).
The hourly grant cleanup is gone. It revoked again every grant whose external
principal was still there after the revoke, and no provider creates such a
principal any more. Open Salto grants are still cleaned up by hand in Salto
KS, see [Salto doors offer only „Per App“](#salto-doors-offer-only-per-app).

- `GRANT_CLEANUP_ENABLED`, `GRANT_CLEANUP_INTERVAL_MS` and the older
  `SALTO_KS_CLEANUP_ENABLED`, `SALTO_KS_CLEANUP_INTERVAL_MS` are ignored and
  can come out of the configuration.
- No migration. The fields of a booking's access entries that record the
  external principal (`principalRemovedAt`, `principalCleanupError`) stay.

## Bank details only encrypted

Change of the storage
([ECCdigital/tickets#16](https://github.com/ECCdigital/tickets/issues/16)).
The customer's bank details of a cancellation request (IBAN, BIC, account
holder, bank) and the tenant's bank account in the invoice application lie in
the database only encrypted, with `CRYPTO_SECRET` (AES-256-CBC), as the
tenants' secrets already do. The API answers the bank details of a
cancellation request only masked: the last four digits of the IBAN, `***` for
every other field given.

The migration `14-10-2026-encrypt-bank-details` encrypts the values stored in
plain text when the backend starts. It writes only fields still in plain text,
so it can run again; values not encrypted yet are read as they are.

### Before the deploy

- `CRYPTO_SECRET` has to be set and 32 bytes long. Without it the backend
  writes no bank details: a cancellation request with bank details or saving
  a tenant with a bank account in the invoice application answers `500`. Where
  bank details still lie in plain text, the migration fails as well and the
  instance stays out of traffic (`/healthz/ready` answers
  `migrations: "failed"`).
- Keep the `CRYPTO_SECRET` the installation runs with today. Without it the
  bank details can no longer be read, nor the tenants' secrets. A change of
  the key is not supported.
- Not covered: cancellation documents (PDF) already in the storage still name
  the IBAN in plain text.
