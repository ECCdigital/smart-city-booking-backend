# Upgrade notes: v4.3.1

What an operator and a client developer need to know when upgrading an
installation from v4.3.0 to v4.3.1.

## Public routes refuse a stale token

Change of the public API ([ECCdigital/tickets#109](https://github.com/ECCdigital/tickets/issues/109)).
A public route that receives an `Authorization: Bearer <token>` header
verifies the token as a protected route does. An expired, revoked or invalid
token is refused with `401` and the same message as on a protected route,
for example:

```json
{ "success": false, "message": "Token has expired" }
```

Until v4.3.0 such a request was answered as anonymous, so a client took the
anonymous answer for its own (an offer behind a login answered
`checkout.login_required` to a signed-in user). Without the header a public
route answers anonymously, as before.

Every route marked `public` is affected: the offers, calendars, checkout,
coupons, booking status, media files and the HTML and JSON engines.

Not affected are the public routes under `/auth` (`/auth/signin`,
`/auth/signup`, `/auth/refresh`, `/auth/resend-verification`,
`/auth/forgot-password`, `/auth/reset-password`, `/auth/verify-email`, the
SSO and card routes, the hooks `/auth/verify/:hookId` and
`/auth/reset/:hookId`, ...): they do not read the `Authorization` header at
all, so a stale token sent along there is ignored and never answered with
`401`. A client with a stale token can always sign in anew or renew it. The
routes under `/auth` that need a session (`/auth/me`, `/auth/signout`) refuse
a stale token with `401`, as before.

A client must therefore renew the access token on this `401`
(`POST /auth/refresh`) and repeat the request once, or drop the token and
repeat it without the header.

Deploy order: backend v4.3.1 goes out only together with Storefront v1.2.1,
which renews and repeats ([ECCdigital/tickets#108](https://github.com/ECCdigital/tickets/issues/108)).
Deploy the backend, then the Storefront right after it. An older Storefront
sends its access token cookie for a day, while the token expires after
15 minutes (`JWT_EXPIRES_IN`), and does not renew on this `401`. The Admin UI
renews on every `401` already.

## Password change: signed in, with the current password

`POST /auth/resetpassword` changes the password of the signed-in account only,
and only with the current password (ECCdigital/tickets#264). The body is
`{ "currentPassword": "…", "password": "…" }`; an `id` in it is no longer read.
Without a session the route answers `401`, without the current password `400`,
with a wrong one `403`.

The clients of v4.3.0 call the route without a session and without the
current password, so their password change fails against v4.3.1:

- Admin UI: from v4.3.1 on it asks for the current password.
- Storefront: from v1.2.1 on it asks for the current password.

Deploy the backend together with both clients, in one go. A script or
integration that calls the route has to sign in first and send the current
password. The routes for a forgotten password,
`POST /auth/forgot-password` and `POST /auth/reset-password` with the token
from the mail, are unchanged.

## Public bookables name no persons

Change of the public API
([ECCdigital/tickets#260](https://github.com/ECCdigital/tickets/issues/260)).
`GET /api/:tenant/bookables/public` and `GET /api/:tenant/bookables/public/:id`
no longer carry three fields of a bookable, whoever asks, and neither do the
related bookables embedded with `?populate=true`:

- `ownerUserId`, the mail address of the member who created the bookable
  (also gone from the event embedded with `?populate=true`);
- `permittedUsers`, the persons who may book it;
- `bookingDiscounts`, the discounts per person and per role.

`permittedRoles` and `requiresLogin` stay, so a client can still offer the
login. Whether a person may book is the answer of the checkout: the
permission check `GET /api/:tenant/checkout/permissions/:id` (v1) or
`GET /api/v2/:tenant/checkout/permissions/:id` (v2) answers `401` to the
anonymous and `403` to a signed-in person who may not book, and the booking
itself is refused. The discount a person gets is in the answer
of the item validation (`bookingDiscountPercent`), as before. The management
read `GET /api/:tenant/bookables/:id` is unchanged.

The public events name no person either: `GET /api/:tenant/events` and
`GET /api/:tenant/events/:id` leave out `ownerUserId` for the anonymous and
for everybody who reads the public's events rather than the management list.
A role holder who manages the events of the tenant keeps it, on the same
routes. The field also stays out of the snapshot of the bookable a new
self-booking stores (`bookableItems[]._bookableUsed`); bookings made before
keep theirs.

A client or integration that read these fields from the public routes has to
use the checkout instead. Admin UI 4.3.1 no longer reads `permittedUsers`;
Admin UI 4.3.0 keeps working against the backend 4.3.1, because it asks the
permission check too. The storefront never read the fields.

Three more answers give away less, with no step for the operator:

- A checkout refused with `checkout.bookable_unavailable` (and
  `checkout.parent_unavailable`, `checkout.child_unavailable`) no longer
  names the bookings it counted (`params.concurrentBookings`). Capacity,
  booked and remaining amount stay.
- `GET /api/v2/dashboard/summary` counts in `totals.users` every person of
  the instance for the instance owner only. A tenant owner, and staff with
  the dashboard of their tenant, get the persons with an active membership
  in their tenants, each once. `byTenant` is unchanged.
- Creating a person with `PUT /api/users` answers the person without the
  password hash (`secret`), as `GET /api/users/:id` does.
