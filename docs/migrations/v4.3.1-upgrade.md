# Upgrade notes: v4.3.1

What an operator does when upgrading an installation from v4.3.0 to v4.3.1.

## Before the deploy: accounts that differ only in case

From v4.3.1 on, sign-in, signup and forgot password find an account by its
address trimmed and without regard to case
([ECCdigital/tickets#259](https://github.com/ECCdigital/tickets/issues/259)).
Of two accounts whose addresses differ only in case or in blanks around them
(`Erika@example.org` and `erika@example.org`) only one is found then, and the
person behind the other one is locked out of it. Check for such accounts on
every installation before the deploy
([ECCdigital/tickets#283](https://github.com/ECCdigital/tickets/issues/283));
on the deploy evening it is step 2, right after the backup.

### Run the check

`scripts/find-case-duplicate-accounts.js` only reads. It connects like the
backend, through `DB_URL` and `DB_NAME` (or `--dbname`), and needs nothing
v4.3.0 lacks, so it runs in the backend container still on v4.3.0. Copy it
there and run it:

```bash
docker cp scripts/find-case-duplicate-accounts.js <backend-container>:/usr/src/app/scripts/
docker exec <backend-container> node scripts/find-case-duplicate-accounts.js
```

From a checkout of v4.3.1 with access to the installation's database it runs
the same way: `DB_URL=… DB_NAME=… node scripts/find-case-duplicate-accounts.js`.

Exit code `0` and the line
`No accounts whose addresses differ only in case or in blanks around them.`
mean there is nothing to do. Exit code `2` means findings, `1` that the check
failed (no connection, for example). A finding lists every account of the
address:

```
erika@example.org
  - "Erika@example.org" (_id 64f…01, created 2024-05-02, local, unverified): found from v4.3.1 on: no; bookings: 0; roles: none
  - "erika@example.org" (_id 64f…02, created 2025-01-15, local, verified): found from v4.3.1 on: yes; bookings: 3; roles: owner of tenant t1
```

- `found from v4.3.1 on`: `yes` for the account stored trimmed and in lower
  case, which v4.3.1 finds; `no` for the others; `undetermined` when no
  account (or more than one) is stored that way, so v4.3.1 takes whichever the
  database returns first.
- `bookings`: the bookings assigned to the account (`assignedUserId`, the exact
  address as stored).
- `roles`: instance owner, owner of a tenant, roles of a membership in a
  tenant, with the membership's status if it is not `active`.
- `in another spelling`: bookings and roles that name the address in a
  spelling none of its accounts has. Only shown when there are some.

Note the output of each installation in
[ECCdigital/tickets#283](https://github.com/ECCdigital/tickets/issues/283).

### What to do with findings

- An account with `bookings: 0` and `roles: none` is deleted, as long as one
  account of the address remains. If none of them has bookings or roles, keep
  the one with `found from v4.3.1 on: yes` and delete the others.
- Every other finding - two accounts of an address with bookings or roles, no
  account to keep with `yes`, or bookings and roles `in another spelling` -
  keeps the installation on v4.3.0. It is upgraded on its own once the
  accounts are resolved with customer support.

Delete after the backup and by `_id`, with `mongosh` against the
installation's database:

```js
db.users.deleteOne({ _id: ObjectId("<_id from the check>") });
```

Not in the Admin UI: v4.3.0 looks the address up in lower case first, so
deleting `Erika@example.org` there deletes `erika@example.org`. Run the check
again afterwards; it has to answer exit code `0` before the deploy goes on.
