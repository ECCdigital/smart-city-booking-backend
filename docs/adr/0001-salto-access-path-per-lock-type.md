# Salto KS: access path per lock type, remote open provisions nothing

Salto KS doors without a keypad are being procured, so remote open (with a self-computed OTP — Salto's `otp_enabled` cannot be switched off) is mandatory next to the proven Guest+PIN path. We decided that the access path follows the **lock type**, not the provider: keypad locks (`escutcheon_pin`, `wall_reader_pin`) support `authorization | remote | both` and default to `both`; every other lock type supports only `remote`. For remote open the platform provisions **nothing** at Salto — no guest, no access group, no seat; the booking is the authorization, the tenant's system user opens, and our own access log ties the opening to the booking. Guest+PIN stays one guest per booking with just-in-time grant and active deletion; seat exhaustion is a provisioning failure with admin notification, not a fallback path. Rejected: remote as default everywhere (unproven at the door, needs a phone), a permanent user per door with time-schedule windows (one PIN for concurrent bookings), and per-guest attribution at Salto (would need an IQ activation per guest).

Consequences: the provider must derive `supportedModes` from `lock_type` and drop `remote` while the lock's IQ is not activated; IQ activations (PIN + secret, encrypted) live per IQ on the tenant's Salto application, one Salto site per tenant.

Status 2026-08-25: remote open is **proven** on the accept site — the backend opened "Tür 01" via `PATCH …/locking` with a self-computed OTP after activating the system user purely via the API. The 2026-08-19 `otp_invalid` failures were caused by app-side activation rotating the secret, not by the path itself (see `docs/adr/0002-salto-iq-activation-via-api-only.md`). The decision stands unchanged; the integration path is specified in `docs/specs/salto-ks-remote-open.md`.
